# ADR 0043: The Android app (Phase 5, slices 1 to 3)

Date: 2026-10-22. Status: accepted by the owner in chat (including the application id and installing a JDK and the Android command-line SDK locally). Phase 5. Builds on [0042](0042-sync-and-bearer-tokens.md) (bearer tokens, pull, push, devices), [0038](0038-two-factor-totp.md) (two-factor), [0041](0041-pwa.md) (the web app stays online-only; the phone is the offline client) and the Android path in `docs/PLAN.md`.

## Context

The server side is finished: the app can sign in with a bearer token, pull eight tables with tombstones, push entry and transfer mutations and be listed and signed out under Settings. What is missing is the app. It must never lock the owner out, never lose or double-count an entry, and never leak financial data (logs, backups, screenshots). The owner tests on a real phone. This Mac has no Java and no Android SDK today.

This ADR covers the first three slices: the project, sign-in with token storage, and the read-only mirror. Offline entries (slice 4) and the remaining screens, signed APK and updates (slice 5) get their own ADR amendment when we reach them.

## Decisions

- **Project.** `apps/android`: Kotlin, Gradle (Kotlin DSL and a version catalog), Jetpack Compose, Material 3, Hilt, Retrofit with kotlinx.serialization, Room, WorkManager. Exact versions are pinned when slice 1 is built. Minimum Android 10 (API 29) so the Keystore and BiometricPrompt behave the same everywhere we test; target the current stable API level. Application id `app.ledgerline.android` (permanent once an APK is installed, confirmed by the owner).
- **Server address.** The owner types it on first run (the app is self-hosted, so nothing is built in). HTTPS only: release builds refuse cleartext. A debug build may allow cleartext to a host the tester enters, so the app can be tried against a scratch server; the debug-only network configuration lives in `src/debug`, never in release.
- **API client.** Generated from `docs/openapi.json` with a pinned generator at build time and not committed. CI fails if the generated client no longer compiles, so an API change that breaks the app is seen in the pull request that makes it. Money is `{ amount, currency }` with `amount` as `Long`; the app never uses floating point for money and formats only for display.
- **Headers.** One interceptor sets `Origin` to the server address and `User-Agent: Ledgerline-Android/<version> (<model>)` on every request, and `X-Ledgerline-Client: android` on sign-in and the two-factor code check only (ADR 0042). `Authorization: Bearer <token>` goes on every other request. The token is never put in a URL or a log line. Release builds log nothing from the network or database layers; debug logs never include amounts, payees or notes.
- **Sign-in.** Address, email and password, then the two-factor code (or a backup code) when the server asks. The token is read from `set-auth-token` and stored only after sign-in fully completes. A password alone for a two-factor account stores nothing.
- **Token storage and lock.** The token is encrypted with an AES-GCM key in the Android Keystore that needs a successful BiometricPrompt (strong biometrics, with the device PIN as fallback) to use. The app locks when it goes to the background for more than a short, fixed time and on cold start. If the key is lost or invalidated (a new fingerprint enrolled, a reset lock screen), the app does not crash or wipe data: it shows "Sign in again", which uses the password and two-factor path and replaces the key. The server never sees the lock, so password and two-factor sign-in always work as the way back in.
- **Sign out.** Calls the server's sign-out route, then deletes the token and the local mirror. If the server cannot be reached, the app still deletes both locally and says that the session stays listed under Settings until it is removed there.
- **Privacy on the phone.** Backups and device transfer are off (`allowBackup=false`, no cloud backup rules), the recents screen and screenshots are blocked while privacy mode is on, and the database lives in the app's private storage (Android file encryption); the app does not add its own database encryption in version 1. Revisit if the owner wants it.
- **Theme.** Material 3 colours generated from the same OKLCH seed and tokens as the web app (teal, zinc surfaces, red only for errors and Delete), by a small script that writes a Kotlin colour file from `packages/ui`; a test fails if the file is out of date. Light, dark and system themes, 48 dp touch targets, TalkBack labels, and a privacy mode that hides amounts.
- **Mirror (slice 3).** Room tables mirror the eight pulled tables as stored rows, with `deleted_at` kept so tombstones stay. Per-table cursors are stored in Room and advance only after the page they belong to is committed in one Room transaction, so a crash re-reads a page instead of skipping one. Rows apply by id and only when the incoming `version` is newer (entry tags by `updatedAt`), as ADR 0042 specifies. A pull with no cursor is a full refresh; the app does one on first sign-in, after "Sign in again", on a cursor error and on a manual "Refresh everything" in Settings. A full refresh replaces rows in one transaction rather than clearing first, so a failed refresh leaves the old mirror intact.
- **Sync work.** A pull when the app opens and a WorkManager periodic job (about every 15 minutes, network required). A 401 stops the job and shows "Sign in again" on next open; it never deletes the mirror. Slice 3 sends nothing to the server except the pull and sign-in.
- **Slice 3 screens** (read-only, enough to prove the mirror and use it): accounts with balances computed locally (opening balance plus the sum of its live entries, never stored), a transactions list with account, category and tag names joined from the mirror, and a "last updated" line. No add or edit yet.
- **Building and installing.** CI builds the app and runs its JVM unit tests. For the owner's phone, CI also uploads a debug-signed APK as a workflow artifact for sideloading (Settings, install unknown apps). A debug APK is signed differently from the future release APK, so moving to release means uninstalling first, which is safe because the mirror is rebuilt from the server. Local builds use a JDK and the Android command-line SDK installed on the development machine.
- **CI.** The Android steps join the existing single `check` job and run only when `apps/android`, `docs/openapi.json` or the colour script changes (decided with `docs/CI.md`, which slice 1 updates). Documentation-only pull requests stay on the light check.

## Not changing

The server, the API contract, the web app, the backup manifest and the restore drill (the phone adds no server tables). Money as integer minor units, UUIDv7 ids, ledger scoping, soft deletes and the rule that logs never contain amounts, payees or notes all apply on the phone too. No analytics, crash reporters or trackers.

## Slices, risks and checks

1. **Skeleton.** Project, theme, generated client, CI job, a first screen that asks for the server address. Nothing can lock the owner out or lose data (no sign-in yet, no network call to production). Checks: CI build and unit tests; the colour file is current; the client compiles against the committed `openapi.json`.
2. **Sign-in, token storage and lock.** Risks: a lock that cannot be opened; a token lost when the Keystore key is invalidated; a token stored after only a password. Mitigations: "Sign in again" always available and never destructive; the token is stored only after the full sequence; password and two-factor on the server are untouched. Checks: unit tests on the sign-in state machine with recorded responses (password only, two-factor, backup code, wrong code, rate limit); the existing bearer and two-factor API tests; manual on the owner's phone against a scratch server first, with a lost-key case (enrol a second fingerprint) before ever signing in to production.
3. **Read-only mirror.** Risks: a wrong cursor or tombstone handling hiding or resurrecting rows (the server is never changed, so no data can be lost there); a failed refresh leaving a half-empty mirror. Mitigations: cursors advance with their page in one transaction; full refresh replaces in place. Checks: unit tests with recorded pull pages (paging, tombstones, repeats, out-of-order versions, a crash between pages); a script that signs in to a scratch server, pulls, and compares the mirror's rows and computed balances with the API's; a final manual comparison on the phone against the scratch ledger. Production is touched only by a read-only pull, and only after the owner says so.

Later (own ADR amendment): 4. Offline entries and transfers through the push (an outbox that survives process death; `superseded` and `rejected` results shown, never dropped). 5. Remaining online screens, the signed release APK and the signing-key backup (a lost key blocks every future update, so it is backed up like the age key and never committed).
