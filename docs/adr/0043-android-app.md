# ADR 0043: The Android app (Phase 5)

Date: 2026-10-22. Status: accepted by the owner in chat (including the application id and installing a JDK and the Android command-line SDK locally). Phase 5. Builds on [0042](0042-sync-and-bearer-tokens.md) (bearer tokens, pull, push, devices), [0038](0038-two-factor-totp.md) (two-factor), [0041](0041-pwa.md) (the web app stays online-only; the phone is the offline client) and the Android path in `docs/PLAN.md`.

## Context

The server side is finished: the app can sign in with a bearer token, pull eight tables with tombstones, push entry and transfer mutations and be listed and signed out under Settings. What is missing is the app. It must never lock the owner out, never lose or double-count an entry, and never leak financial data (logs, backups, screenshots). The owner tests on a real phone. This Mac has no Java and no Android SDK today.

This ADR covers the first three slices: the project, sign-in with token storage, and the read-only mirror. Offline entries (slice 4) and the remaining screens, signed APK and updates (slice 5) get their own ADR amendment when we reach them.

## Decisions

- **Project.** `apps/android`: Kotlin, Gradle (Kotlin DSL and a version catalog), Jetpack Compose, Material 3, Hilt, Retrofit with kotlinx.serialization, Room, WorkManager. Exact versions are pinned when slice 1 is built. Minimum Android 10 (API 29) so the Keystore and BiometricPrompt behave the same everywhere we test; target the current stable API level. Application id `app.ledgerline.android` (permanent once an APK is installed, confirmed by the owner).
- **Server address.** The owner types it on first run (the app is self-hosted, so nothing is built in). HTTPS only: release builds refuse cleartext. A debug build may allow cleartext to a host the tester enters, so the app can be tried against a scratch server; the debug-only network configuration lives in `src/debug`, never in release.
- **API client.** Generated from `docs/openapi.json` with a pinned generator at build time and not committed. CI fails if the generated client no longer compiles, so an API change that breaks the app is seen in the pull request that makes it. Money is `{ amount, currency }` with `amount` as `Long`; the app never uses floating point for money and formats only for display.
- **Headers.** One interceptor sets `Origin` to the server address and `User-Agent: Ledgerline-Android/<version> (<model>)` on every request, and `X-Ledgerline-Client: android` on sign-in and the two-factor code check only (ADR 0042). `Authorization: Bearer <token>` goes on every other request. The token is never put in a URL or a log line. Release builds log nothing from the network or database layers; debug logs never include amounts, payees or notes.
- **Sign-in.** Address, email and password, then the two-factor code (or a backup code) when the server asks. The token is read from `set-auth-token` and stored only after sign-in fully completes. A password alone for a two-factor account stores nothing.
- **Token storage and lock.** The token is encrypted with an AES-GCM key in the Android Keystore that needs a successful BiometricPrompt (strong biometrics, with the device PIN as fallback) to use. The app locks when it goes to the background for more than a short, fixed time and on cold start. If the key is lost or invalidated (a new fingerprint enrolled, a reset lock screen), the app does not crash or wipe data: it shows "Sign in again", which uses the password and two-factor path and replaces the key. The server never sees the lock, so password and two-factor sign-in always work as the way back in.
- **Sign out.** Calls the server's sign-out route, then deletes the token and the local mirror. If the server cannot be reached, the app still deletes both locally and says that the session stays listed under Settings until it is removed there.
- **Privacy on the phone.** Backups and device transfer are off (`allowBackup=false`, no cloud backup rules), the recents screen and screenshots are blocked while privacy mode is on, and the database lives in the app's private storage (Android file encryption); the app does not add its own database encryption in version 1. Revisit if the owner wants it.
- **Theme.** Material 3 colours generated from the same OKLCH seed and tokens as the web app (teal, zinc surfaces, red only for errors and Delete), by a small script that writes a Kotlin colour file from `packages/ui`; a test fails if the file is out of date. Light, dark and system themes, 48 dp touch targets, TalkBack labels, and a privacy mode that hides amounts.
- **Mirror (slice 3).** Room tables mirror the eight pulled tables as stored rows, with `deleted_at` kept so tombstones stay. Per-table cursors are stored in Room and advance only after the page they belong to is committed in one Room transaction, so a crash re-reads a page instead of skipping one. Rows apply by id and only when the incoming `version` is newer (entry tags by `updatedAt`), as ADR 0042 specifies. A pull with no cursor is a full refresh; the app does one on first sign-in, after "Sign in again", on a cursor error and on a manual "Refresh everything" in Settings. A full refresh replaces rows in one transaction rather than clearing first, so a failed refresh leaves the old mirror intact.
- **Sync work.** A pull when the app opens and a WorkManager periodic job (about every 15 minutes, network required). A 401 stops the job and shows "Sign in again" on next open; it never deletes the mirror. Slice 3 sends nothing to the server except the pull and sign-in.
- **Slice 3 screens** (read-only, enough to prove the mirror and use it): accounts with balances computed locally (opening balance plus the sum of its live entries, never stored), a transactions list with account, category and tag names joined from the mirror, and a "last updated" line. No add or edit yet.
- **Building and installing.** CI builds the app and runs its JVM unit tests. For the owner's phone, CI also uploads a debug-signed APK as a workflow artifact for sideloading (Settings, install unknown apps). A debug APK is signed differently from the future release APK, so moving to release means uninstalling first, which is safe because the mirror is rebuilt from the server. Local builds use a JDK and the Android command-line SDK installed on the development machine.
- **CI.** The Android steps join the existing single `check` job and run only when `apps/android`, `docs/openapi.json` or the colour script changes (decided with `docs/CI.md`, which slice 1 updates). Documentation-only pull requests stay on the light check.

## Not changing

The server, the API contract, the web app, the backup manifest and the restore drill (the phone adds no server tables). Money as integer minor units, UUIDv7 ids, ledger scoping, soft deletes and the rule that logs never contain amounts, payees or notes all apply on the phone too. No analytics, crash reporters or trackers.

## Slices, risks and checks

1. **Skeleton.** Project, theme, generated client, CI job, a first screen that asks for the server address. Nothing can lock the owner out or lose data (no sign-in yet, no network call to production). Checks: CI build and unit tests; the colour file is current; the client compiles against the committed `openapi.json`.
2. **Sign-in, token storage and lock.** Risks: a lock that cannot be opened; a token lost when the Keystore key is invalidated; a token stored after only a password. Mitigations: "Sign in again" always available and never destructive; the token is stored only after the full sequence; password and two-factor on the server are untouched. Checks: unit tests on the sign-in state machine with recorded responses (password only, two-factor, backup code, wrong code, rate limit); the existing bearer and two-factor API tests; manual on the owner's phone against a scratch server first, with a lost-key case (enrol a second fingerprint) before ever signing in to production.
3. **Read-only mirror.** Risks: a wrong cursor or tombstone handling hiding or resurrecting rows (the server is never changed, so no data can be lost there); a failed refresh leaving a half-empty mirror. Mitigations: cursors advance with their page in one transaction; full refresh replaces in place. Checks: unit tests with recorded pull pages (paging, tombstones, repeats, out-of-order versions, a crash between pages); a script that signs in to a scratch server, pulls, and compares the mirror's rows and computed balances with the API's; a final manual comparison on the phone against the scratch ledger. Production is touched only by a read-only pull, and only after the owner says so.

Later (own ADR amendment): 4. Offline entries and transfers through the push (an outbox that survives process death; `superseded` and `rejected` results shown, never dropped). 5. Remaining online screens, the signed release APK and the signing-key backup (a lost key blocks every future update, so it is backed up like the age key and never committed).

## Amendment (2026-10-22): hand-written API types with a contract test, and the SDK level

- **No generated client.** Building slice 1 showed that the generator (openapi-generator, Kotlin and Retrofit) does not suit this contract: it makes every response object extend `HashMap` (about 217 models), the Kotlin compiler crashes on the sync push mutation model, the names come from the path (`ApiV1LedgersLedgerIdSyncGet200ResponseChangesAccountsInner`), and its generated `ApiClient` logs whole request and response bodies by default, which would put amounts and payees in the log. The owner chose hand-written types for exactly the routes the app uses (`apps/android/api-client`), each added in the slice that uses it.
- **The contract still guards them.** A JVM test (`ContractTest` and `SchemaContract`) reads the committed `docs/openapi.json` and fails when a Kotlin type differs from its schema: a property missing or extra, required against optional (a default value), nullable against not, a string enum that differs, or an integer the contract allows to be larger than an `Int` (money and every unbounded integer are `Long`). The test also proves it can fail, with deliberately drifted types. An API change that breaks the app therefore fails the pull request that makes it, as the generated client was meant to do.
- **SDK level.** The current Compose and Hilt releases need `compileSdk` 37, so the app compiles and targets API 37 (minimum stays Android 10). The Gradle wrapper is pinned with a checksum.
- **Colours.** `infra/scripts/android-tokens.mjs` writes `LedgerlinePalette.kt` from `packages/ui/src/tokens.css`; `infra/scripts/android-tokens.test.mjs` fails when the committed file is out of date.

## Amendment (2026-10-22): minimum Android 11, and sign-in as built (slice 2, part 1)

- **Minimum Android 11 (API 30).** The owner's phone runs a far newer release, and API 30 is the first where a Keystore key bound to a biometric prompt can also accept the device PIN, which the lock (part 2) relies on. The earlier "Android 10" is replaced.
- **Sign-in as built.** One interceptor puts `Origin` (the saved address) and `User-Agent: Ledgerline-Android/<version> (<model>)` on every request; a sign-in or code check also carries `X-Ledgerline-Client: android` and never a bearer token, and every other request carries the bearer token and never that header. There is no logging interceptor and no cookie jar; the two-factor challenge cookie is read from the sign-in reply and sent back by hand on the code check, held in memory for that step only. Redirects are not followed, so a token cannot be sent to another address. A password for an account with two-factor on gives no token even if the reply carries one; a successful reply without a token is an error, never a half signed-in state. Failures are told apart (wrong password, wrong or expired code, rate limit, address not accepted, server error, no connection). The token is held in memory only in this part, so closing the app signs out; the encrypted, biometric-locked storage is part 2.
- **Checks.** JVM tests against a mock server cover every sequence and failure above (the reply shapes are those pinned by the API's bearer and two-factor tests; these routes belong to the auth library and are not in `docs/openapi.json`), plus tests of the screens' logic. Beyond that, the sign-in was replayed by hand against a scratch API; the owner then runs it on the phone against that scratch server.

## Amendment (2026-10-22): the lock as built (slice 2, part 2)

- **Keeping the session is the owner's choice, right after sign-in.** Storing the token under a key that needs the fingerprint takes one confirmation, so after a sign-in the app asks "Stay signed in on this phone?" with one primary button. Confirming stores the token; Not now keeps the session in memory only (closing the app or being away for 60 seconds signs out); a cancelled or failed confirmation stores nothing and leaves the choice open. A phone with no fingerprint or screen lock set up gets no offer and a plain explanation.
- **The lock is in the app, over a hardware-backed key.** The token is stored encrypted with an AES-256-GCM key in the Android Keystore (it never leaves the phone's secure storage and is excluded from backups), and the app asks for the owner's fingerprint or screen lock before it stores or opens the token. The key itself does not demand a confirmation. Two stricter designs were built first and failed on the owner's phone (a Samsung Galaxy running Android 17): a key tied to one confirmation per use failed with the Keystore error "key user not authenticated" for both fingerprint and pattern, and a key unusable until a confirmation, with a 10 to 30 second window and a retry, still failed on the first fingerprint after setup and after the app had been away, while the pattern worked only after waiting seconds. The phone's Keystore passed the fingerprint confirmation on unreliably, so the owner chose the app-level lock. What it gives up: code running inside the app on a rooted or compromised phone could open the token without the prompt. What it keeps: a lost or borrowed phone is stopped by the prompt and the screen lock, the stored token is useless off the phone, and the token is never in plain text on disk. A benefit for slice 3: background sync can use the stored token while the app is locked, which a key demanding a fresh confirmation for every use would have prevented.
- **Locking.** The app starts locked when a token is stored. It locks after 60 seconds in the background, measured with the monotonic clock (so changing the phone's date cannot extend it), and from a Lock now button; locking forgets the in-memory token. The lock screen opens the system prompt once on arrival and has Unlock and Sign in again instead. With no stored token, locking is a sign-out.
- **A lost key is not a lock-out.** If the saved sign-in can no longer be opened (the phone's screen lock or fingerprint removed so the prompt cannot be satisfied, app data cleared, a damaged copy), the app deletes only its local copy and shows sign-in with a notice that says the old sign-in stays listed under Settings, Signed-in devices until it is removed there or expires. Password and two-factor sign-in on the server are untouched. Sign in again instead of unlocking does the same without needing the old token. A cancelled prompt just stays locked; the phone's own limits on failed attempts apply, and the app tells the owner when it refuses for a while.
- **Sign out** ends the server session, then deletes the stored token and its key. An expired session (401) does the same with a notice.
- **Checks.** Unit tests of the session and lock rules with the storage replaced by a fake (every transition above, the 60-second boundary, cancelled, failed and lost-key unlocks, nothing stored unless confirmed). The Keystore and the prompt cannot run on the JVM, so they are checked on a real phone against a scratch server with the checklist in the pull request: confirm, cancel, lock now, background past and under 60 seconds, force-stop and reopen, remove the screen lock, sign out, and the device name in Signed-in devices. Not yet built: hiding the app in the recents screen and from screenshots (with the privacy mode).

## Amendment (2026-10-22): the mirror as built (slice 3, part 1: tables and pull engine)

- **Tables.** Eight Room tables hold the pulled rows as the server stores them, each keyed by the ledger and the row id, with `deletedAt` kept so a tombstone stays a tombstone, plus one cursor row per ledger (the cursor and the server's time at the last page, which is the "last updated" line). Money is `Long` minor units plus a currency code; text enums stay strings so a value a newer server adds cannot break a pull. Screens read only rows with no `deletedAt`.
- **One transaction per page.** A page and the cursor that follows it are written in one Room transaction, so a crash re-reads a page and never skips one. A row replaces the stored one only when its `version` is higher; an entry-tag link, which has no version, only when its `updatedAt` is later (compared as instants, not text, because the server may write fractions of a second differently). A repeat, an older copy or an out-of-order page therefore never undoes a newer row or a tombstone.
- **Full refresh, as built.** The decision above ("replaces rows in one transaction rather than clearing first") is met by atomicity, not by upserting: the engine reads every page into memory first, then in one transaction deletes the ledger's rows, writes the pulled ones and saves the cursor. A failed download or a failed write leaves the old mirror and cursor exactly as they were. It replaces whatever versions are held, because a server restored from a backup can have lower ones than the phone. It also drops another ledger's rows, so a different account on the same phone never sees the previous one's data. Memory is the cost (the whole ledger is held once); that is fine for a personal ledger and is revisited if one ever outgrows it.
- **Triggers.** No cursor, or a cursor the server answers with 400, starts a full refresh; otherwise pages apply one by one. A 401 returns "signed out" and never touches the mirror; no connection or a server error changes nothing. One pull runs at a time. A server that keeps saying there is more with the same cursor ends the pull as failed instead of looping.
- **A cache, for now.** The database may be dropped and rebuilt when its schema changes (the next pull refills it). That stops being acceptable when slice 4 adds an outbox of entries not yet sent: that slice must use real migrations and keep the outbox out of any destructive path. The schema is exported to `apps/android/app/schemas` for that.
- **Checks.** 20 JVM tests run the real Room database (Robolectric): first pull, paging, a failure on a later page, a crash between a page and its cursor (the fault is injected inside the transaction), tombstones and older repeats, duplicate rows in one page, tag links by `updatedAt`, a refresh that drops rows and accepts lower versions, a refresh that fails while downloading and while writing, a rejected cursor, 401, offline, server error, a stuck cursor, two ledgers, the largest allowed amounts, a page larger than the id chunk, and sign-out wiping everything. Breaking the version rule or the transaction in the code makes four of them fail. The contract test also covers the pull's types, and its checker now reads the `type: ["string", "null"]` form the pull schema uses.
- **Still to build in slice 3:** the prompt-free token read for the background job, the WorkManager job and the pull on open, wiping the mirror on sign-out, the read-only screens, and the script that compares the mirror with the API on a scratch ledger.

## Amendment (2026-10-22): when the mirror is pulled and deleted (slice 3, part 2)

- **The background token.** `TokenProtector.readForSync()` opens the stored token without the prompt. Only the sync uses it (its own HTTP client, through `SessionManager.tokenForSync()`, which prefers the open token); every request the owner makes on a screen still uses the token opened by the lock. It returns nothing when the phone no longer has a screen lock or fingerprint, so the background job never outlives the rule that such a sign-in counts as lost (the next unlock signs out).
- **Which ledger.** The first ledger the server lists, remembered on the phone; forgotten on a new sign-in, on sign-out and when the server answers 404 for it (the next pull looks again). A picker can come later.
- **When it pulls.** A full refresh after every sign-in and on "Refresh everything"; an incremental pull on unlock and when the app comes back to the front while unlocked (at most every 30 seconds); a WorkManager job every 15 minutes with a network, queued only while the session is kept on the phone (after "Stay signed in", and on every start while a token is stored), cancelled when the session ends. The job retries a failed run up to three times with backoff, then waits for the next period.
- **When it deletes.** A sign-out (also when the server could not be reached) and a lost key delete the mirror, the cursors and the ledger choice. The deletion waits for a pull that is writing, so a page cannot land after it. A 401, in the foreground or the background, ends the session once as expired (never after a clean sign-out) and keeps the mirror; the next sign-in replaces it with a full refresh. Starting the app while signed out deletes nothing (a sign-out cut off by the process dying could leave the mirror until the next sign-in replaces it; the data stays in the app's private storage).
- **Checks.** Unit tests of the token rules (read without a prompt while locked, the open token preferred, nothing without a screen lock, a 401 ending the session once) and, on the real Room database, of every transition above: sign-in with and without keeping the session, a cold start while locked, the background pull while locked without a prompt, retries, 401 in the foreground and background, sign-out, sign-out without the server, a lost key, a sign-out during a pull that is writing, a new sign-in, the 30-second gap, a ledger that disappears, no ledgers, no connection and no readable token. A WorkManager test checks one unique job every 15 minutes that needs a network and that cancelling removes it. On the phone (part 3): the job runs while the app is locked and in the background.

## Amendment (2026-10-22): the read-only screens and the scratch comparison (slice 3, part 3)

- **Screens.** After sign-in the app shows two tabs, Accounts and Transactions, under one line that says when the mirror was last brought up to date (the server's time of the last page, in the phone's time zone), "Updating…" while a pull runs, or that the phone is offline or could not update and is showing what was saved (with Try again). Pull down to refresh; a menu holds Refresh everything, Lock now and Sign out. Before the first full refresh has finished the lists say "Getting your ledger…". The sign-in proof (the list of ledgers) is gone.
- **Accounts** show the balance the server would show: the opening balance plus the sum of the account's cleared, live entries (signed amounts), computed by one SQL query on the phone and never stored; pending entries are left out of the balance and counted under it. A client's or loan's balance account (`contactId` set) is hidden, as on the web; archived accounts come after the others under "Archived".
- **Transactions** list live entries newest first (date, then time, then creation) with the account, category and live tag names joined from the mirror, 100 at a time with Show more. A transfer leg without a payee is "Transfer", a split entry "Split". Amounts use tabular figures and the currency's own decimals (`BigDecimal`, never floating point; Android's currency data comes from ICU's CLDR, as the server's `Intl` does). Each row is read by TalkBack as one sentence; targets are at least 48 dp.
- **The scratch comparison** is a JVM test (`MirrorMatchesServerTest`), not a separate script, so it checks the app's own engine and queries: it signs in to a server (password and two-factor code), makes changes through the REST API (accounts, categories, tags, a tagged entry, income, a pending entry, a split entry, a transfer), pulls with the app's engine into a real Room database and compares every live account's balance and name and every live entry (amount, base amount, account, category, kind, status, payee, date, version, tags, split lines, and the tag names the screen shows) with the API. Then it edits, deletes, clears, adds, renames and deletes the transfer, pulls incrementally, compares again, and checks that the incremental mirror equals a fresh full pull row for row, tombstones included. It runs only when `LEDGERLINE_COMPARE_ORIGIN` is set (CI skips it) and writes to the ledger, so it is pointed at a scratch server only. It passed against the scratch server on 2026-10-22; counting pending entries in the balance made it fail, as did the matching unit test.
- **Not yet:** privacy mode and hiding the app from the recents screen and screenshots (FLAG_SECURE), a ledger picker, Home and the other online screens (slice 5), and entries made offline (slice 4).

## Amendment (2026-10-22): offline entries and transfers (slice 4, design approved by the owner)

Slice 4 adds entries and transfers made on the phone with or without a connection, sent through the existing push (`POST /ledgers/{id}/sync`, ADR 0042). No server change.

- **Outbox.** A Room table holds one row per change, in the order it was made, with a UUIDv7 mutation id made on the phone (also the idempotency key, and for a create the new entry's id or the transfer's `transferId`), the type, the body, `baseVersion` and `editedAt`. A row leaves the outbox only in the same transaction that applies the server's result for it, so a send cut off at any point is simply sent again and the server answers `replayed`. Editing or deleting a change that has not been sent folds into it (an edit changes the pending create; a delete of a pending create removes it), so the server never sees half a story.
- **Real migrations from now on.** The database stops being rebuilt on a schema change (the fallback in slice 3 part 1 is removed): version 2 adds the outbox with a written migration and a migration test with rows in place. Mirror tables can still be refilled by a full refresh; the outbox never is.
- **What the screens show.** The mirror stays the server's copy. Lists and balances read the mirror with the outbox laid over it: a new entry appears marked "Not sent yet", an edit shows its new values, a delete hides the row. Because the overlay is computed, a full refresh cannot hide or undo an unsent change.
- **When it sends.** Each sync sends first, then pulls: after a save when online, on opening, on pull to refresh, and in the 15-minute background job (which may use the stored token while locked, as for the pull). At most 50 mutations per request, oldest first. A network failure or an unexpected server error sends the same batch again later.
- **Results.** `applied` and `replayed` clear the row. `superseded` (changed or deleted on another device) and `rejected` (with the server's reason) move the change to a **Needs your attention** list and are never dropped: a superseded change offers **Keep mine** (sent again against the current version) or **Keep the other**; a rejected one offers **Edit** or **Discard**.
- **Forms (owner's choice).** A central Add button opens an expense or income form built to take under five seconds: amount, account, category and date (today) first; payee, tags and note optional. Entries can be edited and deleted from their row. Transfers: between two accounts of the same currency, without fee, bonus or exchange rate. Split entries, transfer fees and bonuses and cross-currency transfers stay on the web for now; a split entry is read-only on the phone and says "Edit on the web". Typed amounts become minor units exactly (`BigDecimal`); more decimals than the currency allows is an error, never rounded.
- **Signing out with unsent changes (owner's choice).** Sign out first says how many changes are not sent and offers **Send now** when online; deleting them takes a separate red "Sign out and delete N unsent changes". A 401 keeps the outbox; it is sent after signing in again to the same ledger. Changes made for another ledger are kept and shown, not sent there.
- **Risks and checks.** Losing the outbox on an app update: migration test, no rebuild fallback. A change applied twice: a batch sent, its reply dropped and sent again must come back `replayed` with one row on the server. The app dying between the reply and clearing the outbox: a fault injected in that transaction, then the same rows after the next send. A lost conflict: a web edit and an offline edit of the same entry must leave the phone's version in the attention list. A refresh hiding unsent work: a full refresh with outbox rows in place. Wrong amounts: parsing tests and balances including unsent entries compared with the server after they are sent. The scratch test grows into a convergence test (offline changes, competing web edits, a cut-off batch, then push, pull and compare everything with the API), and the owner checks on the phone in airplane mode (add, edit, delete, force-stop, reopen, back online: each change arrives exactly once).
- **PRs.** (1) This amendment. (2) Outbox, migration, push types with their contract test and the send engine, no UI. (3) Sending in every sync and the background job, and the attention list. (4) The forms, the unsent marks and the attention screen. (5) The convergence test and the phone check.

## Amendment (2026-10-22): the outbox as built (slice 4, PR 2: no screens yet)

- **Database version 2** adds the `outbox` table through Room's automatic migration (adding a table needs no hand-written SQL), and the drop-and-rebuild fallback is gone. A test builds a version 1 database from its exported schema file, with rows in it, and opens it as version 2: every row survives and Room accepts the schema.
- **Sign-out** now deletes the mirror tables only; the outbox is deleted only by an explicit `clearAll()`, which the confirm step in PR 4 will call. Until the forms exist nothing can enter the outbox.
- **One lock** (`SyncLock`) is shared by the pull, the push and the sign-out wipe.
- **A batch is re-sent until it is answered.** Taking a batch marks its changes as sent once; they stay at the head of the queue until the server's results are saved, so a lost reply or a crash before saving sends exactly the same changes again, and the server answers `replayed`. A change marked as sent is never altered again: a later edit becomes its own change, with `baseVersion` counting the changes still in flight (an edit made while its create was in flight expects version 1).
- **Versions.** An entry's `baseVersion` is its mirrored version; a transfer's is its outgoing leg's (the leg with the negative amount), which is what the push compares. A change for an entry or transfer the phone does not know is refused on the phone, never sent with a made-up version.
- **Results.** The rows each result carries are written into the mirror (by version, without moving the pull cursor) in the same transaction that clears or marks the change. A result status this app version does not know is kept for the owner like a rejection. Keep mine is not offered when the other device deleted the row (only Keep the other remains).
- **Contract.** The push request and response types are checked against `docs/openapi.json` like the pull's. The checker learned three rules: a free-form object (`body`) is a JSON object in Kotlin; a contract default makes a request property optional (not a response property); and an optional property the contract never makes null is a nullable Kotlin property with a null default, which is left out when sent (a test checks the encoded mutation).
- **Checks.** Outbox rules (folding, versions, batches per ledger, settling, a crash while settling, Keep mine, Keep the other, the sign-out wipe keeping the outbox), the send engine against a stand-in server that applies each id once (120 changes in batches of 50, a lost reply, a crash before saving, an edit while its create was in flight, 401 and no connection, rejected changes not blocking the rest, another ledger's changes), the migration, and UUIDv7 ids matching the server's pattern. Allowing an edit to change a change already sent, saving results without a transaction, or removing the migration each fails exactly the matching tests.

## Amendment (2026-10-22): sending in every sync (slice 4, PR 3)

- **Send, then pull.** Every sync (unlock, the app coming back to the front, pull to refresh, Refresh everything and the background job) sends the outbox for the mirrored ledger first and pulls after. If the send stops on a refused token, no connection or a ledger the server does not know, the sync ends there with that result (a pull would fail the same way, and a refused token ends the session once as before, keeping both the mirror and the outbox). Any other failure of the send (a server error) still lets the pull run; the send's result is kept for the screens.
- **After a save.** The screens call `changed()`: while the app is unlocked the change is sent at once with a pull; and when the session is kept on the phone a one-time WorkManager job is queued that waits for a network, so a change saved offline is sent as soon as the phone is back online even if the app has been closed. A session not kept on the phone sends only while the app is open. Ending the session cancels both jobs; the outbox stays.
- **For the screens.** The outbox gives a live count of unsent changes and a live list of superseded and rejected ones; Keep mine, Keep the other and Discard act on that list (the screens come in PR 4).
- **Checks.** Send before pull (the order is recorded), a refused token or no connection while sending skipping the pull and keeping the outbox, a server error while sending still pulling, `changed()` unlocked, locked (queued, then sent by the background job) and with a session not kept, sign-out keeping unsent changes, and the one-time job (one at a time, network required, cancelled with the session). Pulling before sending, or pulling after a refused token, fails the matching tests.

## Amendment (2026-10-22): unsent changes on screen, the attention list and the sign-out question (slice 4, PR 4a)

The tag always wins over the number in the Gradle file (owner's choice).
- **Workflow** `.github/workflows/android-release.yml`, started by `android-v*` tags: `version` (valid tag, commit on `main`), `checks` (the full suite through `ci.yml` on the tag), `release` (the `android-release` environment, which needs the owner's approval, holds the four secrets). The release job decodes the keystore into `RUNNER_TEMP` with mode 600, builds, always deletes the key, verifies with `apksigner` (and against the repository variable `ANDROID_CERT_SHA256` when it is set, an addition so a wrong key can never publish), and publishes a GitHub Release with the APK, a `.sha256` file and both hashes in the notes, not marked latest. A missing secret stops the job with an error naming it; secrets are passed only to the build step's environment and never echoed. There is no pull-request dry run of the signing steps (owner's choice); the Gradle logic is covered by a local build with a throwaway key.
- **Owner's steps** (key, age-encrypted backup with a restore test, environment, secrets, certificate pin, the tag command) are in `apps/android/README.md`.
- **Checked locally** with a throwaway keystore: unsigned without the variables or with one missing, signed with all four (`apksigner verify`, `aapt2 dump badging` shows the version name and code from the environment), the decode, verify and fingerprint-comparison steps of the workflow run by hand (accepts the fingerprint with or without colons and in either case, refuses another). The workflow itself first runs when the owner tags.
- **Found by the first real run:** the environment's tag rule must be added as a *tag* rule (a branch rule `android-v*` refuses a tag push), and the verify step must not depend on one exact `apksigner` label; it reads the digest loosely, requires 64 hex digits and prints nothing else from `apksigner`. A tag runs the workflow file as it was at that tag, so a fix needs a new tag.
- **Second finding:** the runner's newest build-tools print no certificate line, so the check runs `infra/scripts/android-verify-apk.sh` with the pinned build-tools 36.0.0, and the pull-request `android` job runs that script on a throwaway-signed build, so this class of failure is caught before a tag.
- **No second suite on the tag (owner's choice).** The first two release runs spent about 25 minutes re-running the full suite on a commit that `main` had already tested, then failed at the signature step. The workflow now checks that the tag is on `main` and that `main`'s `check` passed on that commit (`infra/scripts/main-check-passed.sh`, tested with a stand-in `gh`), and goes straight to the owner's approval. A server release still runs the full suite on its tag.
