# ADR 0035: Tags

Date: 2026-10-19. Status: accepted by the owner when approving the design in chat (every recommended choice). Builds on [0005](0005-paired-transfers.md), [0007](0007-category-splits.md), [0014](0014-red-delete-actions.md), [0023](0023-transfer-bonus.md) and [0025](0025-transfer-fee.md); extends [0033](0033-csv-export-format.md) and [0034](0034-csv-import.md) in a later step.

## Context

Categories answer "what was this for"; sometimes the owner also wants a free-form label that cuts across categories, such as a trip or a reimbursable cost. PLAN.md promised free-form tags in a later phase.

## Decisions

- **A tag is a label, nothing more.** It never changes a balance, a budget, a report or any total. No existing money query reads tags; a test compares accounts, Home and both reports before and after tagging.
- **Two tables (migration 0025).** `tags` (ledger, name, `archived_at`, version, and the usual `created_at`, `updated_at`, `deleted_at`) and `transaction_tags` (ledger, entry, tag, and the same timestamps). Both have UUIDv7 ids and composite ledger keys, so a link can only join an entry and a tag of the same ledger. Names are unique per ledger ignoring case and surrounding spaces among live tags, archived ones included.
- **Name rules.** 1 to 40 characters, no commas, no semicolons, no control characters (so a CSV tags column is unambiguous), and at most 10 tags per entry. The database enforces the name rule.
- **Endpoints.** `GET/POST /tags`, `GET/PATCH/DELETE /tags/{id}`, `POST /tags/{id}/archive` and `/unarchive`, under the usual ledger prefix, with `expectedVersion` and `Idempotency-Key`. Each tag carries `usageCount`, the live entries that have it (a transfer counts once). Entries accept `tagIds` on create and edit (omitted keeps the tags, `[]` clears them) and return `tags: [{ id, name, archived }]`. `GET /transactions` and the transactions export accept one `tagId` and return whole entries that carry it.
- **Archive hides, it does not forbid.** An archived tag disappears from pickers but stays on its entries, still filters, and may still be assigned through the API. Rename and archive keep every link because entries point at the tag, not its name.
- **Delete only when unused.** A tag that a live entry carries cannot be deleted (409; archive it instead). Deleting an unused tag also drops its links on deleted entries, so Undo of such an entry brings it back without the tag. Tag delete has no Undo; an unused tag is cheap to create again. Delete buttons are red (ADR 0014).
- **Entries and Undo.** Links belong to the entry: deleting an entry leaves its links alone and Undo brings the tags back with it. Editing tags changes the entry's version.
- **Splits.** Tags belong to the entry, not to a split line.
- **Transfers.** A transfer is tagged as one thing and the same write puts the same tags on both legs. The transfer's fee and bonus are separate entries and do not inherit its tags; they can be tagged on their own.
- **Recurring rules** carry tags in a later step; an entry a rule creates then copies them.
- **Concurrency.** Assigning and deleting tags take the ledger lock entry writes already use, so a tag cannot vanish while an entry is being tagged.
- **Backup and restore.** The manifest fingerprints `tags` and `transaction_tags`, a derived `tags` check records live, archived and deleted tags and the live links on live and on deleted entries, and the restore drill's `tag_links` invariant requires every live link to point at a live tag of its ledger, no entry to carry a tag twice and both legs of a transfer to carry the same tags. The scratch drill (seed with all three tag states) and two negative cases cover it.
- **Privacy.** Logs record that a request happened, never tag names.
- **Not in this version.** Reports by tag (a possible later Insights addition), merging tags, filtering by several tags at once, tags on split lines.
