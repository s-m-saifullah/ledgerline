# ADR 0041: Installable web app (PWA)

Date: 2026-10-21. Status: accepted by the owner when approving the design in chat (every recommended choice). Phase 4 slice 4. Builds on the deployment facts in `CLAUDE.md` (the web container serves the static build and proxies `/api`) and [0040](0040-accessibility-pass.md).

## Context

Ledgerline should install to a phone's or computer's home screen and open like an app. It must never keep financial data in a browser cache, never trap a browser on an old release, and never get in the way of sign-in, two-factor or the API. Real offline data is the Android app's job (Room), not the web app's.

What exists today: a favicon, an SVG icon and a 180 px touch icon; Caddy serves `index.html` for any path that is not a real file and already sends `no-store` for `index.html`; the content security policy (`script-src 'self'`) already allows a same-origin service worker and manifest.

## Decisions

- **Manifest and icons.** A web app manifest (name Ledgerline, standalone display, start page and scope `/`, theme and background colours from the design tokens) and PNG icons at 192 and 512 px plus a maskable 512 px, drawn from the existing favicon mark. No custom install banner: the browser's own install option is enough.
- **A small hand-written service worker** (no Workbox). It handles only same-origin GET requests and **never anything under `/api`**; those go straight to the network, so nothing financial is ever cached. Hashed `/assets/*` files are cached on first use (they never change under the same name). Page loads are network first, with the cached shell used only when the network fails; offline the shell opens and the existing load-error screen shows for the data.
- **Updates.** The cache name carries the release version; the new worker takes over at once (skip waiting, claim clients) and deletes old caches when it activates. Because page loads are network first and assets are hashed, a new release replaces the old shell on the next load.
- **Registration only in production builds,** so local development and the browser specs are unaffected.
- **Caddy.** `sw.js` and the manifest are sent with `Cache-Control: no-store`, and a missing `sw.js` is a real 404 instead of the app shell.
- **Kill switch.** If a worker ever misbehaves, a release that ships a `sw.js` which unregisters itself and clears its caches clears it from browsers, since `sw.js` is never cached.

## Not changing

No API, data, auth or backup change; no migration. Light and dark themes, WCAG AA and the other UI rules stay as they are.

## Rollback

A worker installed by this release stays in browsers if the release is rolled back. It keeps working (page loads are network first), but it is part of the rollback note in the release record.

## Slices and checks

1. This ADR (docs only). 2. Manifest, icons and the manifest link. 3. The service worker, the Caddy headers and tests: unit tests for the routing rules; a browser spec against a production build that checks the worker installs, a page load works offline from the shell, an `/api` request fails offline instead of coming from a cache, and a second build with a different version replaces the first after a reload; the read-only production smoke check also confirms the manifest and `sw.js` headers. Each is web or Caddy only; nothing can lose data, and the worst case (a stale shell) is covered by the kill switch above.
