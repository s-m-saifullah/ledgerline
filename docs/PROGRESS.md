- **2026-11-09:** Android, slice 3 of [ADR 0050](adr/0050-money-writes-on-the-phone.md): the shared pieces every phone write will use (Android only; no screen, no server change; built, not merged or released). **New:** `WriteKeys` (one `Idempotency-Key` per change, sent again unchanged on a retry, a new key when the change differs, made from a prefix and a UUIDv7 and never from the change text, so an amount or a name cannot reach a header or a log); `WriteError` with `Written.toWriteError()` (offline, forbidden, failed, or the server's own sentence); `Written.isStale()` (a `409` or `404`: read the screen again and show the sentence); and `WriteCopy` with `WriteError.text(...)`, so each screen keeps its own words while the type and the rules are shared. **Budgets moved onto them** with every sentence, key and reload unchanged (its 100 tests pass, with `LimitError` renamed to `WriteError` in three test files and nothing else changed); Categories and the editor's New category still have their own copy of the same pattern and were left alone on purpose. **Tests:** 7 for the keys (reuse, a new key for a changed change, clear, prefix, the server's key rule `^[A-Za-z0-9._:-]{8,128}$`, no change text in a key) and 5 for the errors and the stale rule. 22 deliberate mutations; 21 caught. **One survivor, kept on purpose:** the `keys.clear()` Budgets runs after a write went through cannot be seen, because opening and closing the sheet clear the keys too and a finished write always closes it; the line stays so a finished write's keys never linger in memory. The full Android unit suite and lint pass. The money sheet itself is built with its first user, receive payment (slice 4), so it can be checked on the owner's phone. Next: slice 4.
- **2026-11-09:** Android, slice 2 of [ADR 0050](adr/0050-money-writes-on-the-phone.md): a person still on a temporary password who signs in on the phone is told why nothing loads (Android only; no server change; checked on the owner's phone over wireless debugging against a scratch server: the message for a person on a temporary password, then a normal sign-in with a new password, a two-factor sign-in, and no leftover device from the refused sign-in; not merged or released). Sign-in itself succeeds (the sign-in routes are open) and every data route then answers `403`, so the phone used to show only "Could not update". **Now:** when a sign-in is finished (after the code, for an account with two-factor) the app asks `GET /api/v1/me` with the new token **before the session has it**, through a one-off client (`ClientsProvider.forToken`; the token is never stored while it asks). If `mustChangePassword` is true the app ends that sign-in on the server at once (best effort), keeps no session and no stored token, goes back to the first step with the email kept, and says "Choose a new password on the web, then sign in here again." Any other outcome (no answer, a dropped connection, an error status, an unreadable reply) signs in as before: the server still refuses what it must. Changing the password stays on the web. New: the hand-written `Me` type and `LedgerlineApi.me()`, checked against `openapi.json` by the contract test. **Tests:** 9 new view-model cases (the question carries the new token and the session never passes through the offer state, the unused sign-in is ended with the same token, the message stands when that sign-out fails, each kind of failed question still signs in, the two-factor path asks only after the code and starts over at the password, a wrong password asks nothing) and a content case, plus two contract cases; the existing sign-in cases changed on purpose because a sign-in now makes a second request. 13 deliberate mutations, all caught. Screenshots at 320 and 390 dp, light and dark, and with the largest text: the line wraps cleanly in the existing error style. The full Android unit suite and lint pass. Next: the shared online-write helper and the money sheet.
