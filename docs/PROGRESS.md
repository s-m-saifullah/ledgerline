- **2026-11-04:** Cleared ledgers, slice C of five ([ADR 0049](adr/0049-deleted-people-and-cleared-ledgers.md)): the **API for clearing a ledger and undoing it** (API 0.1.55, migration 0029 `ledgers.cleared_at`; merged as #230 on the owner's word, not released). **New routes only:** a person clears their own ledger (`POST /ledgers/{id}/clear`, the body must be the word `CLEAR`, owner only) and restores it (`POST /ledgers/{id}/restore`), both with an `Idempotency-Key`; the admin does the same for a person's ledger (`POST /users/{id}/ledger/clear` and `/ledger/restore`, no key, never their own id, never a deleted person) and gets back the person and a date, never anything from the ledger. A clear soft-deletes every live row of every table of the ledger with one moment; the ledger, its name, its currency and the memberships stay. A restore brings back exactly those rows, for 30 days (to the millisecond) and only while the ledger has nothing live in it (`409`, "Clear what is there now first."). One undo slot: clearing again removes the older batch at once. The hourly job removes a batch 30 days after the clear, one transaction per ledger (a ledger it cannot remove is left whole and the others still go; counts only in the log). **New fields, additive and optional in the schema:** `clearedAt` on the ledger and `ledgerClearedAt` on `ManagedUser` (the Android model gets `clearedAt` with a null default, so an older server still decodes). **Found and decided on the way (ADR amended):** a clear and a restore raise every row's `version`, because the phone keeps a row only when its version is higher; the saved answers to retried writes are cleared too, so an old key answers `409` afterwards; clearing an empty ledger changes nothing, so a second press cannot throw the undo away; the removal also takes rows deleted before the clear, because one of them can point at a row in the batch and the database would refuse; two clears at once need the ledger held (a new opt-in `exclusive` on the write runner, off for every existing route). **Tests:** 50 new API tests (a clear and a restore field for field, versions, roles, the word, replay, the boundary to the millisecond, a restore racing the removal, a ledger that cannot be removed, two writers at once, a phone's sync before and after, the admin's routes, isolation: another person's ledger byte for byte the same, and the isolation walk now names the two routes). 73 deliberate mutations; 12 first slipped through (no test held the ledger while two writers waited, the two moments of two clears were identical, the admin's own account was refused by a second guard, a person without a ledger and a deleted ledger's date were never tried, an extra field in the body), each now caught, except one equivalent (the operation text of restore, because the body already differs) and one redundant guard that was removed. **Restore drill:** a new invariant, "a ledger that records a clear has nothing live older than it", with a negative case. **CI found an old race in the browser tests, fixed here:** `more-layout.spec` measured a group the moment the Settings link showed, and on Linux the group is sometimes not drawn yet (a null box). It failed on `main`'s own commit as well (34 of 101 runs against 38 of 101 on this branch, in a Linux container matching CI), and passes 101 of 101 now that the measuring helper waits until the element is visible. Counts: web 1393, ui 50, api 739, shared 100. Next: slice D, the web screens.
