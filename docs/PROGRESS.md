- **2026-11-04:** Deleted people, slice B of five ([ADR 0049](adr/0049-deleted-people-and-cleared-ledgers.md)): the **API for deleted people** (API 0.1.54, no migration; merged as #229 on the owner's word, not released). **New routes only, admin only:** `GET /users/deleted` (people deleted less than 30 days ago, newest first, with `deletedAt` and `purgeAt`), `POST /users/{id}/restore` (the person, sign-in, ledger and memberships that the delete removed, exactly as they were: same password, two-factor and stopped or allowed sign-in; sessions stay ended; never something deleted earlier or separately) and `DELETE /users/{id}/purge` ("Delete now": the person and everything of theirs removed for good). **The hourly tick** removes everyone whose 30 days are over, one transaction each, so a person it cannot remove is left whole and the others still go; it never removes the admin and logs counts only. A restore and a purge at the same moment queue on a row lock. A ledger another live person is a member of stays; if something there still points at the person the database refuses (`409`, nothing removed). A new person's email that belongs to someone deleted now says how many days are left to restore them (the web shows its own text until slice D). **Tests:** 31 new API tests (restore leaves money rows byte for byte the same and revives only what that delete removed; a purge removes every kind of row, proved against the database's own table list, and leaves another person's ledger unchanged; the 30-day boundary to the millisecond on an injectable clock; the lock tests; the failure paths), the isolation test now also checks the new list, and its seeding moved into a shared `ledger-fixture.ts`. 60 deliberate mutations; 6 first slipped through (no check that the sign-in came back, nothing stamped like another person's delete, no test person with two-factor rows or a stranger's verification row, and one redundant guard that was removed), each now caught. **Restore drill:** a new invariant, "a deleted person has nothing live left" (the draft's "no live row under a deleted ledger" would fail after any delete, so the ADR is amended), with two negative cases; run on a scratch database in its own compose project (removed afterwards): a clean drill (21 tables, 14 derived checks), all negative cases and the concurrent-write drill passed. Counts: web 1393, ui 50, api 689, shared 100. Next: slice C, clear and undo for a ledger (migration 0029).
