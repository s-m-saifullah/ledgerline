- **2026-11-12:** Privacy: **a switch for the rate fetch, a complete sign-out wipe on the web, and no rate saved while amounts are hidden** (merged as #265; not released: the server part ships with the next server tag, the phone part with the next Android release; no migration, API contract unchanged). **`RATES_ENABLED`** (default `true`, in `.env.example`): the daily exchange-rate fetch is the server's only outside call, and with `false` nothing leaves the server. The hourly job skips the rate step (the other three steps still run), a manual refresh answers 200 with every currency not fetched (the way an outage already looks, so no contract change), and rates are set by hand; `buildApp` now chooses its rate source from the config, so no single wrong line in `server.ts` can reach the network. **Web sign-out:** it removed nine named cache keys, so budgets, reports, loans, currencies, recurring rules, imports and others stayed in memory for up to five minutes; it now removes every cached answer but the session entry (set to nobody, so a page watching the session sees the sign-out, which `client.clear()` would not guarantee) and clears finished changes, which hold what was typed. **Hourly helper, web and phone:** "Use this total" wrote `3.5 h at $40.00/h` into the saved description even in privacy mode; with amounts hidden it now fills the amount and leaves the description alone. **Tests:** written first (7 new API tests and 3 web tests failed on the old code; the phone's tests could not run before the change because of a compile error, so the phone mutations cover them); API 773, web 1,474 and Android unit tests pass, with type check, Biome, Android lint and the browser tests in CI; 20 deliberate mutations, all caught. One existing web assertion changed on purpose (`forgetSession` no longer leaves unrelated cache entries). Run on no phone: only a description string and privacy mode changed.

- **2026-11-12:** Ops: **a daily health watch tells the owner when something fails** (merged as #263; not released: the report script reaches the server with the next server tag, or by hand; no migration, API contract unchanged). **Why:** nothing alerted the owner; a failed nightly backup, a full disk, a dead container or an expiring certificate showed only in `backups/cron.log` or by opening the app. **What it does:** the new `Health watch` workflow runs daily at 09:00 UTC and by hand, and a failed run is the alert (GitHub emails the owner). Its `public` job needs no secrets: `PUBLIC_URL/api/health` must answer and the certificate must have more than 14 days left. Its `server` job runs in a new unprotected `monitoring` environment, because the protected `production` environment would wait for a reviewer every day, with its own SSH key that the server lets run one read-only script and nothing else. `infra/scripts/health-report.sh` fails when the newest finished backup is 26 hours old or more, when the off-site copy is on and its last upload failed or is 48 hours old or more, or when disk use is 85% or more; it prints ages and percentages only, and over SSH it accepts only `check HOURS PERCENT` and refuses every other command. The workflow holds `contents: read`, has no push or pull request trigger and never touches the deploy key. **Tests:** 38 new tests, written first (they failed with the script missing), run on macOS and on Linux with the real `df` and `stat`; 38 deliberate mutations, all caught (the first run missed five gaps in the tests, now closed). The infra suite passes. **Proven on 2026-11-12:** the owner did the one-time setup (a key locked to the report in the server user's `authorized_keys`, the `monitoring` environment limited to the `main` branch with its three secrets, the report copied by hand until the next server tag carries it); a manual run was green, a run with `max_dump_hours` 0 failed in the `server` job only (the `public` job passed), and the failure email arrived. The steps are in `docs/SELF_HOSTING.md`, "Health watch", and `docs/CI.md` describes the workflow.
- **2026-11-12:** Server: **the API survives a lost database connection, looks the session up once per request, and logs why four background steps failed** (merged as #261; tagged `v0.7.2` on `main`'s merge of it after `main`'s own check passed; release run 43176186637 passed its checks (scope, unit, three browser shards, Android) and built the images, and its deploy waits for the owner's approval in the protected `production` environment, so the release is not live yet; no migration, API contract unchanged at 0.1.55). **The crash:** when PostgreSQL restarted or dropped a connection, `pg` emitted `error` on the connection itself; the pool listens only for idle connections and removes its listener while a request uses one, so a connection lost in use, or ended by the server for sitting idle in a transaction, ended the whole API process. Run for real against a scratch PostgreSQL with its container restarted under the running server: the old code died and every later request was refused; the new code stayed up, logged one safe line, failed the one request in flight and answered the next 149 of 150. **What changed:** every connection gets its own error listener when it is made, reported once as one JSON line holding only the error class and database code (never the message); the pool gets a 5 s connect limit, a 60 s statement limit and a 120 s limit for a transaction left idle (the owner chose these; a CSV export already stops itself at 120 s), and migrations run without the two database limits so a slow one cannot be cut off at start-up; one helper (`requestSession`) looks the session up once per request for the account guard and the nine places that asked (it was twice on every request); the catch-up after saving a recurring rule, the daily rate refresh and the two hourly removals now log their error class and database code instead of swallowing the error. **Tests:** 20 tests failed first (including the process crash); the API suite is 763 tests and passes against a real PostgreSQL, with type check and Biome; 28 deliberate mutations were all caught. One existing assertion changed on purpose: the deleted-people test now expects two error log lines (the count and one per person it could not remove) instead of one. One new test (a connection dropped mid-request) also passed on the old code, so it did not start red. **Also in this release:** the backup and deploy script fixes of #258, whose deploy path runs for real for the first time with this tag: the deploy takes a backup and drills that exact dump before it pulls anything, and stops with nothing changed if either fails. **After the deploy** (server commands are the owner's): the deploy log should show `Restore drill passed for backups/...` twice (before and after), `backups/` should hold a fresh dump, and `/api/health` should answer.
- **2026-11-12:** Android, released `android-v0.3.1`, a fix release (merged as #259; tagged on `main`'s merge of it after `main`'s own check passed; the `release` job waited for the owner's approval in the `android-release` environment; the signed APK `ledgerline-android-0.3.1.apk` and its SHA-256 are on the GitHub release; no server update is needed). **Signed out while locked.** Home read for the life of the app, also under the lock screen. With the app locked there is no token in memory, so the read went out without one, the server answered 401 and the app deleted the saved sign-in as if it had been refused; a background pull writing a new cursor while the app sat locked was enough. `OnlineReader` and `OnlineWriter` now send nothing when no token is open, and a 401 ends the session only if the token that was sent is still the open one; Home now reads only while it is shown, as Loans does. **One person's figures under the next sign-in.** The screens kept their last answer across a sign-out (`MonthlyRead` kept it by month, not by ledger), so on a shared phone the next person could see the last person's figures until their own first pull arrived. `readOnTrigger`, `PagedRead` and `MonthlyRead` now show Loading and forget their answer when the mirror has no ledger or the ledger changes (Home, Budgets, Insights, Clients and Loans). **Not checked on a phone:** the sign-out was found by reading the code and never reproduced on a device; the owner is to lock the app past a background pull and unlock. **Tests:** the Android suite is 2,227 tests (542 of them screenshot tests, skipped unless asked) and passes, with lint; 11 new tests failed first; 11 deliberate mutations were all caught. The background sync was found to be already safe (`SyncRunner.run` sends nothing without a readable token), so only a regression test was added there. One new Home test timed out once on the slower CI runner: after a wipe the mirror's two watched queries can report in either order, so Home may read the old ledger once more and use the one queued answer; the test now answers by ledger. It did not reproduce locally under load, so that cause is likely, not proven.
- **2026-11-12:** Server scripts: **backups cannot stop for good, and the deploy proves its backup restores** (merged as #258; not released: it ships with the next server tag, whose deploy is the first real run of these changes). `scheduled-backup.sh` now prunes first (a failed backup, a full disk being the likeliest cause, used to skip the prune, so space was never freed and every later night failed the same way), writes `Low disk space` to the cron log under 200 MB (`MIN_FREE_MB`) and exits 1 while still trying the backup, and exits 1 on a failed backup or drill; `prune-backups.sh` ignores a dump without a checksum when it counts the newest three. `deploy.sh` decides a fresh install by the database volume (`ledgerline_db`, or `COMPOSE_PROJECT_NAME`'s), starts a stopped database, takes the backup and drills that exact dump (the new `backup-and-drill.sh`) before anything is pulled, and stops with nothing changed if either fails; it refuses when a database container exists without the expected volume, keeps the older rollback target when the same version is deployed twice, and retries the health check. The release workflow's post-deploy backup now fails the step when it fails (a `;` let a failed backup drill an older dump and stay green). `docs/SELF_HOSTING.md`, `CLAUDE.md` and the drill-test README match. **Tests:** 143 of 143 infra script tests pass on Linux (the deploy tests need `flock`, so they skip on macOS); 20 tests failed first; 36 deliberate mutations were all caught. Run for real against a scratch PostgreSQL: the helper, the nightly script (also with a forced low disk), `deploy.sh` with a stand-in only for the image pull, the volume-mismatch refusal, and the workflow's own post-deploy command.
